# Googleスプレッドシート連携

GitHub Pagesの画面から呼び出す、所有者実行のApps Script Webアプリです。読み取り・集計・本人確認・入力列への保存をサーバー側で行います。最初の設定では書き込みを無効にします。元のマッチングDB／KPIの値・数式は初期設定で変更しません。原本への保存は複製での実検証と所有者の明示的な有効化が完了するまで拒否します。

## 設定する前に

1. 指定のGoogleスプレッドシートを独立したファイルへ複製し、別のバックアップも保管します。共有とファイルIDを確認します。
2. 複製に「2期目マッチングDB」（gid `286330650`）と「2期目月間KPI・KGI」（gid `2007683505`）があることを確認します。ファイルのタイムゾーンを `Asia/Tokyo` にします。原本のタイムゾーンを変更する必要はありません。
3. 複製の「拡張機能 → Apps Script」で `Code.gs` を保存します。「プロジェクトの設定」でマニフェスト表示を有効にし、`appsscript.json` を保存します。
4. 所有者アカウントで `setupNode` を実行し、Googleが表示するスコープを確認して承認します。Sheets REST APIが無効のエラーになる場合は、関連するGoogle Cloudプロジェクトで **Google Sheets API** を有効にします。

初期設定は `_NODE_players` と `_NODE_operations` の2つのアプリ専用タブを追加し、既存の候補者行へROW DeveloperMetadataの管理IDを追加します。業務セルは書き換えません。アプリ専用タブは所有者以外の編集を保護します。初期設定は所有者のシートUIで実行してください。

## 初期ログイン情報

設定時に `ADMIN` と次の7名の高エントロピーパスワードを生成し、所有者だけが見るダイアログに一度表示します。この画面を閉じる前に安全な場所へ控えてください。ログ・シート・公開ソースにはパスワードを保存しません。Script Propertiesにはランダムsalt・HMAC hash・サーバー秘密値だけを保存します。

| --- | --- |
| ND-001 | 越前祐美 |
| ND-002 | 鈴木楓 |
| ND-003 | 櫻庭奈々 |
| ND-004 | 髙田侑弥 |
| ND-005 | 佐藤光 |
| ND-006 | 倉島颯汰 |
| ND-007 | 佐々木駿 |

初期チームは `NODE`、ひとことは空、目標は初期設定用の20件です。実際の目標へ修正してから運用してください。`_NODE_players` の `sheetNames` はJSON配列です。担当列Dの呼び名が表示名と違う場合は、所有者が例えば `['表示名','実際の担当表記']` を有効なJSON（ダブルクォート）にして対応づけます。別メンバーで同じ別名を使えません。表示名だけを編集しても既存D列の担当名を変更しません。

ログイン情報を失った場合は「NODE連携 → パスワードを再発行」を所有者が実行します。対象のセッションは無効になります。IDを知っているだけではログインできません。公開されているフロントエンドへ初期パスワードやGoogleの認証情報を埋め込まないでください。

## Webアプリの公開

「デプロイ → 新しいデプロイ → ウェブアプリ」で、実行ユーザーを **自分（スクリプト所有者）**、アクセスできるユーザーを **全員** にします。組織の設定で匿名Webアプリが許可されない場合は、管理者へ確認してください。GitHub Pagesの連携設定には `/exec` で終わるデプロイURLを入力します。

公開エンドポイントの `GET` と `health` は設定有無・書き込み可否・protocolだけを返します。名簿、候補者、シートの値、認証情報は返しません。他の操作はランダム256bitセッショントークンが必要です。セッションは6時間で失効し、ログイン失敗は既存アカウントごとに15分間5回まで制限します。存在しないIDは単一の失敗カウンターを共有し、公開アクセスでIDごとのScript Propertyを増やせないようにしています。各リクエストでサーバーがロールと有効なアカウントを確認します。

APIを編集した際は、新しいバージョンでWebアプリの既存デプロイを更新してください。フロントエンドを公開しただけではApps Scriptのデプロイは更新されません。

## 複製シートで確認すること

書き込みが無効のまま管理者／本人でログインし、元シートと集計が一致するか確認します。本人には本人の人材明細だけが返り、ランキング用には表示名と集計値を返します。サンプルデータはサーバーにありません。

- 面談は「同日・同担当ID・同候補者名」を1件として重複除外します。提案以降は管理IDで提案行を区別します。紹介人数は候補者IDの重複を除きます。
- 候補者IDは担当IDとスペースを除いた候補者名から生成します。同じ担当に同姓同名の別人がいる場合は識別できません。運用前に確認し、必要なら独立した候補者IDマスタを導入してください。
- 集計日はJSTの業務日です。シートのDate値／`YYYY-MM-DD`・`YYYY/M/D`を読みます。「停止」、不正日、空欄は日付イベントにしません。
- C面談実施はQ列です。元KPIが参照するN列との関係は未確認で、N列は変更しません。
- KPIタブには書き込みません。入力列はA/B/C/D/F/G/H/I/J/K/L/M/Q/U/V/W/X/Y/Zのみです。E/N/O/P/R/S/Tを推測で変更しません。
- ヘッダー行は面談実施／会社名／氏名／担当から検出しますが、書き込みには入力対象19列すべてが指定位置の観測ラベルと一致する必要があります。空白・括弧・全角文字は正規化し、観測済みのI／Qの補足だけ明示的に許可します。未知の補足や列の入れ替えは意味を推測せず停止し、警告を表示します。その場合は実績を表示せず、実Googleの複製で列を確認した後に許可ラベルを調整します。
- 紹介元の保存列は未確認です。紹介元はROW DeveloperMetadata `NODE_SOURCE` で保存します。
- 対象セルに数式があると保存を拒否します。新規行も入力列のみを変更するため、既存の数式や書式は保ちます。ただし新規行の数式を自動で延長する実装はありません。原本の数式範囲が十分に延長された複製の空き行で試してください。

確認後、所有者が「NODE連携 → 複製シートの書き込みを有効化」で承認します。このメニューでは元ファイルの書き込みは有効化できません。複製で面談→提案→各工程、ステータス変更、プロフィール編集、ID追加、シートの直接編集後の同期、並べ替え後の保存、二重送信を確認します。新規の面談から別会社への提案行を作る場合は面談日を継承し、同日の面談が重複集計されないことを確認してください。

シートで直接行を追加した場合、所有者が「NODE連携 → 行IDを同期」を実行します。管理IDのない行は取り込み対象外になり、画面に警告が出ます。ROWメタデータが保たれる行全体の並べ替えを使用してください。列だけの並べ替えや一部分の切り貼りで候補者／担当／管理IDがずれる操作は避けてください。

## 実検証後に原本の保存を有効化する

原本へ切り替える前に、**同じApps Scriptプロジェクト**で「NODE連携 → 複製でログイン・保存を実検証」（`verifyNodeCopyIntegration`）を所有者が実行します。独立したコピーかつ書き込み有効のときだけ動作します。これはモックではなく、実際のApps Script／Sheets APIを経由して次を確認します。

1. 検証専用アカウントを発行し、発行パスワードで実際にログインします。
2. 検証専用の面談・提案をコピーへ保存します。読み戻したシートのDate値・氏名・会社・日付・管理IDと、面談の重複除外を確認します。
3. コピーの検証行Gに検証用の数式を置き、APIが数式へのステータス上書きを拒否することを確認します。
4. 検証行の入力セルと行メタデータを消去し、検証アカウントを無効化します。アプリの保存履歴と無効化アカウントは残ります。原本には検証行を作りません。

すべて成功した場合だけ、コピーID・ヘッダーhash・検証項目・所有者・検証日時を含むHMAC署名付きの証明をScript Propertiesへ保存します。後始末を含めて失敗すると証明は発行しません。失敗してコピーに検証データが残った場合は所有者がコピーで状態を確認してください。ログイン情報はログへ出しません。

独立したバックアップを確保し、N／Qの集計差分、実際の保護・数式・担当者名も確認した後、検証から7日以内に「NODE連携 → 検証後に原本の保存を有効化」（`enableNodeOriginalAfterVerifiedCopy`）を実行します。原本の26列のヘッダーが検証したコピーと一致することと、所有者・証明の署名・対象コピーを検査します。所有者が確認画面へ **原本のファイルIDを入力した場合だけ** 移行します。

移行は原本にアプリ専用タブと行メタデータを用意し、コピーで設定した有効なメンバー・aliasesを引き継ぎます。原本の業務セル・数式へ検証データは書きません。原本に同名のアプリ管理タブがある場合は別プロジェクトとの重複を避けるため中止します。セッションはすべて失効するので、画面で再ログインして同期してください。認証情報は同じプロジェクト内で保持され、公開ソースやシートへ転記しません。

単に `writesEnabled` や `originalWriteVerified` を手でtrueにするだけでは原本の保存は開きません。署名証明と有効化日時に結び付いた署名sealが必要です。証明の7日制限は初回有効化時の確認で、明示的に有効化済みの原本が7日後に自動停止することはありません。「書き込みを停止」は原本にも適用できます。

## 保存と再送の扱い

保存にはクライアント生成の `operationId` が必要です。業務セル／行メタデータ／保存履歴を、Sheets `spreadsheets.batchUpdate` の1回のリクエストで原子的に適用します。再送は同じ操作IDを使い、保存内容が違う再利用は拒否します。Google側が保存してから通信が途切れても、同じ操作IDの再送で二重登録しません。保存履歴にはパスワードを含めません。

プレイヤー追加のパスワードはサーバー秘密値と操作IDから256bitの疑似乱数を生成し、同じ操作の再送では同じログイン情報を管理者へ返します。認証hashの準備が終わっても、プレイヤー行の原子的な保存が完了するまではログインできません。

既存の活動・進捗保存には読み込み時の `rowVersion` が必要です。ROW管理IDから現在の行を解決し、内容と数式のfingerprintを比較します。API同士はScriptLockで直列化します。Sheetsで人が直接編集する操作はScriptLockの対象外のため、保存直前に再確認しても非常に短い競合窓は残ります。直接編集とアプリ保存を同時に行わない運用をしてください。

## API v1

`POST` の `Content-Type` は `text/plain;charset=UTF-8`、JSON本文は次の形です。Apps Script ContentServiceのリダイレクトを追従してください。秘密値をURLクエリへ入れません。

```json
{"version":1,"action":"snapshot","token":"SESSION_TOKEN","payload":{}}
```

成功は `{"ok":true,"data":...}`、失敗は `{"ok":false,"error":{"code":"CONFLICT","message":"..."}}` です。HTTPステータスのみで成功を判定しないでください。

| action | payload | data |
| --- | --- | --- |
| health | なし | configured / writesEnabled / protocol |
| login | id / password | token / snapshot |
| snapshot | なし | snapshotそのもの |
| logout | なし | loggedOut |
| saveActivity | activity | snapshot |
| updateStatus | recordId / status / rowVersion | snapshot |
| updateProfile | player | snapshot |
| createPlayer | name / team / target / sheetNames | snapshot / credentials `{id,password}` |

4種類の保存actionは `operationId` が必須です。`snapshot` は `self`・公開プレイヤー項目＋`sheetNames`・本人または管理者の`activities`・全員の期間別`counts`・`syncedAt`・`warnings`・`writesEnabled`を返します。パスワードhash、salt、セッション一覧、内部行番号、保存履歴は返しません。

新しい提案行ではクライアント側のrecordIdを保存せずサーバーがUUIDを採番します。既存の提案に後工程を追加する場合はサーバーから受け取ったrecordIdとrowVersionが必要です。日付は `YYYY-MM-DD`、予定時刻は `HH:mm`、目標は1〜9999の整数です。

`saveActivity` の `memo` が省略されている場合、既存のM列は変更しません。明示的な文字列がある場合だけ更新し、空文字列は明示的なメモ消去として扱います。未変更のメモや確度をUIから空文字の既定値で送らないでください。

## ローカル検証と参照

`node --test tests/apps-script*.test.mjs` はVM上のApps Script／Sheetsモックで確認します。実GoogleのOAuth、匿名Webアプリからのブラウザアクセス、シートの保護と数式の具体的な動作は別途複製ファイルで確認する必要があります。このローカル実装だけでは接続済み・本番稼働済みにはなりません。
