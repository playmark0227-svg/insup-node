# Googleスプレッドシート連携

GitHub Pagesの画面から呼び出す、所有者実行のApps Script Webアプリです。読み取り・集計・本人確認・入力列への保存をサーバー側で行います。今後の保存先は、所有者が作成した新しい管理用スプレッドシートです。移行元の原本は常に読み取り専用で、このコードでは初期設定・管理タブ追加・メタデータ・業務値のいずれも書き込めません。

## データを変えずに移行する

移行には、Googleスプレッドシートの「ファイル → コピーを作成」で作るブック全体のコピーを使います。別IDの新ファイルを管理先にする方針は所有者が承認済みです。既存の空ブックは残します。作成済みコピーの値・数式・書式は代表範囲で照合しましたが、コメントの保全と外部参照の接続は別途確認が必要です。**アプリの実接続と保存の有効化はまだ完了していません。** タブ単位の移行補助 `Migrate.gs` は実行せず、停止ガードを維持します。詳細は [MIGRATION.md](./MIGRATION.md) を参照してください。

1. 元ファイルの全タブを、新しい管理用ファイルへ元のタブ名・値・数式・書式を保って移します。既存のセルを集計し直したり、担当者名を置換したり、数式をアプリ用に変更したりしません。コピー後はタブをまたぐ数式と参照先も確認します。
2. 新しい管理用ファイルに「2期目マッチングDB」と「2期目月間KPI・KGI」が元の名前であることを確認します。タブをコピーして gid が変わっても対応します。コードはタブ名の完全一致と入力19列の見出しを検証して、移行先の実際の gid を保存します。
3. **初期設定前に**、新しい管理用ファイルとは別の、検証用コピーを用意します。テスト候補者・テスト数式を使うのはこの独立した検証用コピーだけです。
4. 新しい管理用ファイルの「拡張機能 → Apps Script」で `Code.gs` を保存します。「プロジェクトの設定」でマニフェスト表示を有効にし、`appsscript.json` を保存します。スプレッドシートのタイムゾーンは `Asia/Tokyo` が必要です。コードは移行元・移行先いずれの設定も自動変更しません。
5. Apps Scriptの「サービス」に **Google Sheets API v4（識別子 `Sheets`）** があることを確認します。配布マニフェストにはこの設定を含めています。表示されない場合は「サービス」の「＋」からGoogle Sheets API・v4・識別子 `Sheets` を選び、追加して保存します。Apps Scriptが作成した既定のCloudプロジェクトでは、サービスの追加・保存によってAPIも自動で有効になるため、Cloud Consoleでの手動操作は不要です。独自の標準Cloudプロジェクトを使う場合のみ、そのプロジェクトでもAPIを有効にします。[Google公式のサービス有効化手順](https://developers.google.com/apps-script/guides/services/advanced)
6. 保存後、新しい管理用スプレッドシートを再読み込みします。所有者アカウントで、シート上部の **「NODE連携 → 新しい管理シートの初期設定」** を選びます。Googleが表示するスコープを確認して承認し、確認ダイアログへ **新しい管理用ファイル自身のID** を入力します。承認後に処理が再開しない場合は、同じメニューを選び直してください。初期設定の `setupNode` はシートのダイアログを使うため、Apps Scriptエディターの「実行」ボタンから起動しません。

以後の初期設定・検証・保存先の有効化・行ID同期・パスワード再発行も、新しい管理用スプレッドシートの「NODE連携」メニューから実行します。検証用コピーを接続中も、操作するメニューはこの管理用スプレッドシート側です。

新しい保存先IDは Script Properties の `NODE_DESTINATION_ID` に登録します。公開ソースやフロントエンドへIDを埋め込む必要はありません。初期登録後は別のファイルを自動的に保存先へ変えません。

初期設定は `_NODE_players` と `_NODE_operations` の2つのアプリ専用タブを追加し、既存の候補者行へROW DeveloperMetadataの管理IDを追加します。移した業務セルの値・数式・書式は変更しません。アプリ専用タブは所有者以外の編集を保護します。この時点ではアプリからの保存は無効です。

## 初期ログイン情報

設定時に `ADMIN` と次の7名の高エントロピーパスワードを生成し、所有者だけが見るダイアログに一度表示します。この画面を閉じる前に安全な場所へ控えてください。ログ・シート・公開ソースにはパスワードを保存しません。Script Propertiesにはランダムsalt・HMAC hash・サーバー秘密値だけを保存します。

| ID | 表示名 |
| --- | --- |
| ND-001 | 越前祐美 |
| ND-002 | 鈴木楓 |
| ND-003 | 櫻庭奈々 |
| ND-004 | 髙田侑弥 |
| ND-005 | 佐藤光 |
| ND-006 | 倉島颯汰 |
| ND-007 | 佐々木駿 |

初期チームは `NODE`、ひとことは空、目標は初期設定用の20件です。実際の目標へ修正してから運用してください。`_NODE_players` の `sheetNames` はJSON配列で、**先頭の名前を新規行のD列へ保存します**。例えば `["越前","越前祐美"]` のように、D列の入力規則で許可された実担当表記を先頭、表示名などの読取用別名を後ろにします。初期値の先頭はID順に「越前・鈴木・櫻庭・高田・佐藤・倉島・佐々木駿」です。検証用コピーにも、この管理マスタの配列と順序をそのまま引き継ぎます。別メンバーで同じ別名を使えません。初期値は新規管理マスタだけに設定し、原本や既存D列の担当名・入力規則は変更しません。

ログイン情報を失った場合は「NODE連携 → パスワードを再発行」を所有者が実行します。対象のセッションは無効になります。IDを知っているだけではログインできません。公開されているフロントエンドへ初期パスワードやGoogleの認証情報を埋め込まないでください。

## Webアプリの公開

「デプロイ → 新しいデプロイ → ウェブアプリ」で、実行ユーザーを **自分（スクリプト所有者）**、アクセスできるユーザーを **全員** にします。組織の設定で匿名Webアプリが許可されない場合は、管理者へ確認してください。GitHub Pagesの連携設定には `/exec` で終わるデプロイURLを入力します。

公開エンドポイントの `GET` と `health` は設定有無・書き込み可否・protocolだけを返します。名簿、候補者、シートの値、認証情報は返しません。他の操作はランダム256bitセッショントークンが必要です。セッションは6時間で失効し、ログイン失敗は既存アカウントごとに15分間5回まで制限します。存在しないIDは単一の失敗カウンターを共有し、公開アクセスでIDごとのScript Propertyを増やせないようにしています。各リクエストでサーバーがロールと有効なアカウントを確認します。

APIを編集した際は、新しいバージョンでWebアプリの既存デプロイを更新してください。フロントエンドを公開しただけではApps Scriptのデプロイは更新されません。

## 読み取りと集計の確認

書き込みが無効のまま管理者／本人でログインし、元シートと集計が一致するか確認します。本人には本人の人材明細だけが返り、ランキング用には表示名と集計値を返します。サンプルデータはサーバーにありません。

- 面談は「同日・同担当ID・同候補者名」を1件として重複除外します。提案以降は管理IDで提案行を区別します。紹介人数は候補者IDの重複を除きます。
- 候補者IDは担当IDとスペースを除いた候補者名から生成します。同じ担当に同姓同名の別人がいる場合は識別できません。運用前に確認し、必要なら独立した候補者IDマスタを導入してください。
- 集計日はJSTの業務日です。シートのDate値／`YYYY-MM-DD`・`YYYY/M/D`を読みます。「停止」、不正日、空欄は日付イベントにしません。
- C面談実施はQ列、稼働開始実績はX列の日付です。「2期目マッチングDB」に保存した実績を「2期目月間KPI・KGI」の数式で集計します。KPI参照・担当名の調整状況は [MIGRATION.md](MIGRATION.md) に記録します。
- アプリの保存処理はKPIタブには書き込みません。入力列はA/B/C/D/F/G/H/I/J/K/L/M/Q/U/V/W/X/Y/Zのみです。E/N/O/P/R/S/Tを推測で変更しません。
- 「現在のステータス」の変更はG列だけを更新し、工程の日付は記録しません。KPIに実績を反映するには、活動登録から工程と日付を入力します。
- ヘッダー行は面談実施／会社名／氏名／担当から検出しますが、書き込みには入力対象19列すべてが指定位置の観測ラベルと一致する必要があります。空白・括弧・全角文字は正規化し、実シートで観測したC列のスペース注意、F列の担当ポジ例、I列のアポ獲得日、J／Q列の入力タイミング、L列の確度割合の補足を明示的に許可します。未知の補足や列の入れ替えは意味を推測せず停止し、警告を表示します。その場合は実績を表示せず、実Googleの複製で列を確認した後に許可ラベルを調整します。
- 紹介元の保存列は未確認です。紹介元はROW DeveloperMetadata `NODE_SOURCE` で保存します。
- 対象セルに数式があると保存を拒否します。新規行も入力列のみを変更するため、既存の数式や書式は保ちます。ただし新規行の数式を自動で延長する実装はありません。検証用コピーの数式範囲を確認してから、コピーの空き行で試してください。新しい管理シートの数式範囲は移行時に変更しません。

シートで直接行を追加した場合、所有者が「NODE連携 → 行IDを同期」を実行します。管理IDのない行は取り込み対象外になり、画面に警告が出ます。ROWメタデータが保たれる行全体の並べ替えを使用してください。列だけの並べ替えや一部分の切り貼りで候補者／担当／管理IDがずれる操作は避けてください。

## 別の検証用コピーで確認し、新しい保存先を有効化する

新しい管理用ファイルに紐付く **同じApps Scriptプロジェクト** を使い、管理用スプレッドシートの **「NODE連携」メニュー** から次を順に実行します。括弧内の関数名はコードを確認するための表記です。

1. 「NODE連携 → 別の検証用コピーを設定」（`setupNodeVerificationCopy`）へ、初期設定前に用意した検証用コピーのIDを入力します。移行元の原本や新しい管理用ファイル自身を指定すると中止します。タブ名・19列・26列全体のヘッダー一致を検査し、コピーへ管理タブと行メタデータを追加します。新しい管理用ファイルの業務セルには触れません。
2. 「NODE連携 → 検証用コピーの書き込みを有効化」（`enableNodeWritesForCopy`）を実行します。この関数は登録した検証用コピーだけで動作します。管理者／本人で再ログインし、面談→提案→各工程、プロフィール・担当者対応、ステータス、二重送信、並べ替え後の保存を確認します。
3. 「NODE連携 → 検証用コピーで実検証」（`verifyNodeCopyIntegration`）を実行します。検証専用アカウントを発行し、検証コピーのグリッド末尾へ新規2行を追加します。その新規2行だけ引き継いだ入力規則を解除するため、既存の厳密な担当名ドロップダウンは変更しません。割当はコピーID・タブID・所有者・専用アカウントに限定し、30分で失効します。ログインした専用アカウント本人がこの2行だけに面談・提案を保存し、日付・氏名・会社・管理ID・面談の重複除外・数式への上書き拒否を確認します。後始末は割り当てた管理IDの2行だけを対象にし、テストの入力セル・行メタデータと割当情報を消去してアカウントを無効化します。空の新規2行・アプリの保存履歴・無効化したアカウントは検証用コピーにだけ残ります。通常の保存リクエストから行番号は指定できません。
4. 後始末まで成功した場合のみ、コピーID・登録済み保存先ID・ヘッダーhash・確認項目・所有者・時刻を含むHMAC署名付きの証明を Script Properties に保存します。実Googleでの検証に失敗した場合、証明は発行せず、新しい管理用ファイルを有効化しません。
5. 検証から7日以内に「NODE連携 → 検証後に新しい管理シートを有効化」（`enableNodeDestinationAfterVerifiedCopy`）を実行し、確認ダイアログへ登録済みの新しい管理用ファイルIDを入力します。所有者・署名・コピー・移行先のタブとヘッダーを再検査します。

有効化は保存先の設定と必要な行メタデータだけを更新します。**新しい管理用ファイルへテスト候補者・テスト数式は作成せず、コピーから業務値やプロフィールを上書きしません。** アプリ専用名簿は最初に新しい管理用ファイルへ設定した内容を保持します。検証用コピーで調整したプロフィールや担当者の別名を運用にも使う場合は、新しい管理用ファイルのアプリ専用名簿に明示的に設定してください。

切り替え時は全セッションが失効するため、画面へ再ログインして同期します。署名証明と有効化日時に結び付いた署名sealが必要なので、設定の `writesEnabled` だけをtrueにしても本番保存は開きません。7日の制限は初回有効化時に適用し、有効化後に自動停止することはありません。管理者の画面にだけ、接続中ファイルの名前と実際のマッチングDB／KPIのリンクを返します。

移行元の原本はこの手順の対象になりません。旧版の `enableNodeOriginalAfterVerifiedCopy` を実行しても常に拒否します。「書き込みを停止」は現在の接続先に適用できます。

## 保存と再送の扱い

保存にはクライアント生成の `operationId` が必要です。業務セル／行メタデータ／保存履歴を、Sheets `spreadsheets.batchUpdate` の1回のリクエストで原子的に適用します。再送は同じ操作IDを使い、保存内容が違う再利用は拒否します。Google側が保存してから通信が途切れても、同じ操作IDの再送で二重登録しません。保存履歴にはパスワードを含めません。

プレイヤー追加のパスワードはサーバー秘密値と操作IDから256bitの疑似乱数を生成し、同じ操作の再送では同じログイン情報を管理者へ返します。認証hashの準備が終わっても、プレイヤー行の原子的な保存が完了するまではログインできません。

既存の活動・進捗保存には読み込み時の `rowVersion` が必要です。ROW管理IDから現在の行を解決し、内容と数式のfingerprintを比較します。API同士はScriptLockで直列化します。Sheetsで人が直接編集する操作はScriptLockの対象外のため、保存直前に再確認しても非常に短い競合窓は残ります。直接編集とアプリ保存を同時に行わない運用をしてください。

## API v1

`POST` の `Content-Type` は `text/plain;charset=UTF-8`、JSON本文は次の形です。Apps Script ContentServiceのリダイレクトを追従してください。秘密値をURLクエリへ入れません。

```json
{"version":1,"action":"snapshot","token":"SESSION_TOKEN","payload":{}}
```

成功は `{"ok":true,"data":...}`、失敗は `{"ok":false,"error":{"code":"CONFLICT","message":"..."}}` です。HTTPステータスのみで成功を判定しないでください。

| action | payload | data |
| --- | --- | --- |
| health | なし | configured / writesEnabled / protocol |
| login | id / password | token / snapshot |
| snapshot | なし | snapshotそのもの |
| logout | なし | loggedOut |
| saveActivity | activity | snapshot |
| updateStatus | recordId / status / rowVersion | snapshot |
| updateProfile | player | snapshot |
| createPlayer | name / team / target / sheetNames | snapshot / credentials `{id,password}` |

4種類の保存actionは `operationId` が必須です。`snapshot` は `self`・公開プレイヤー項目＋`sheetNames`・本人または管理者の`activities`・全員の期間別`counts`・`syncedAt`・`warnings`・`writesEnabled`を返します。管理者だけには `destination: {title, matchingUrl, kpiUrl}` も返します。プレイヤーと公開healthには保存先ファイル情報を返しません。パスワードhash、salt、セッション一覧、内部行番号、保存履歴は返しません。

新しい提案行ではクライアント側のrecordIdを保存せずサーバーがUUIDを採番します。既存の提案に後工程を追加する場合はサーバーから受け取ったrecordIdとrowVersionが必要です。日付は `YYYY-MM-DD`、予定時刻は `HH:mm`、目標は1〜9999の整数です。

`saveActivity` の `memo` が省略されている場合、既存のM列は変更しません。明示的な文字列がある場合だけ更新し、空文字列は明示的なメモ消去として扱います。未変更のメモや確度をUIから空文字の既定値で送らないでください。

## ローカル検証と参照

`node --test tests/apps-script*.test.mjs` はVM上のApps Script／Sheetsモックで確認します。実GoogleのOAuth、匿名Webアプリからのブラウザアクセス、シートの保護と数式の具体的な動作は別途複製ファイルで確認する必要があります。このローカル実装だけでは接続済み・本番稼働済みにはなりません。
